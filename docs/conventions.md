## URL — «pretty URLs», БЕЗ `.html`

- ✅ Правильно: `/proekty/`, `/products/oborudovanie-lvm/`, `/o-kompanii/`
- ❌ Неправильно: `/projects.html`, `/products/oborudovanie-lvm.html`, `/o-company.html`
- Деплой-схема: каждая страница в проде лежит как `<URL-слаг>/index.html` на диске,
  а URL остаётся без расширения и с trailing slash.
- В прототипе файл может называться как угодно (рабочее имя); при деплое rsync кладёт
  его в `<server-path>/<slug>/index.html`. Слаг берётся из `structura.md`.
- В ссылках внутри HTML (header, footer, body) — только pretty URLs.
  Никаких `href="catalog.html"`. Корректно: `href="/products/"`, `href="/proekty/"`.
- Внутренние якоря (`#leadgen`, `#contacts`) — нормально, не путать с URL.
- Правило общее для всего сайта — старый uralinduktor.ru работает так же;
  сохраняем конвенцию для SEO и совместимости 301-редиректов.

## Иерархия URL = хлебные крошки

- URL повторяет путь из breadcrumb 1-в-1. Если крошки
  `Каталог → Дробемётное оборудование → Кранового типа → УИД-376Е`,
  то URL = `/products/drobemetnoe-oborudovanie/kranovogo-tipa/uid-376e/`.
- ❌ Не «выносить» подкатегорию/товар в корень — структура должна читаться из URL.
- Почему: Яндекс кластеризует по структуре URL; старый сайт использовал
  hierarchical URLs (free 1:1 маппинг для 301); менеджеры пересылают URL —
  из адреса видно раздел.
- При переносе/переименовании URL обязательно: (1) nginx 301 со старого;
  (2) обновить все внутренние ссылки (breadcrumb, мегаменю, футер, каталоги);
  (3) обновить structura.md (новый URL + старые → 301); (4) поправить префикс
  в picture.md, если был.
- Глубина — до 4 уровней. Больше — обсуждать.

## Пути к ассетам — ТОЛЬКО абсолютные с `/`

- ✅ `src="/brand/logo-color.png"`, `href="/css/style.css"`
- ❌ `src="../../brand/logo-color.png"`, `src="img/foo.png"`
- Почему: относительные пути работают только на конкретной глубине URL;
  при переезде страницы на другой уровень всё 404'ит.
- Касается всего: `<img src>`, `<link href>`, `<script src>`, `<a href>`,
  `url(...)` в CSS, `srcset`. Якоря (`#contacts`) — исключение.
- Партиалы особенно строги — они вставляются на разной глубине.

## Шапка и подвал — ТОЛЬКО через партиалы

> **Устарело (так было на Astro).** На платформе шапка, мобильное меню и подвал — React-компоненты
> `platform/apps/web/src/components/layout` (`Header.tsx`, `Drawer.tsx`, `Footer.tsx`), одни на все страницы,
> включая Практикум; пункты меню и контакты — админка «Шапка, меню, контакты». Партиалы ниже сайтом
> не используются — см. [`CLAUDE.md`](../CLAUDE.md), «Где что лежит».

Источники правды: `design/prototypes/_partials/header.html` и `_partials/footer.html`.
В страницах эти блоки обёрнуты маркерами `@partial:header` / `/@partial:header`.

- ❌ НИКОГДА не править содержимое между маркерами прямо в файле страницы —
  следующий sync затрёт правку.
- ✅ Менять меню/футер — только в партиале, затем:
  `python3 design/prototypes/build/sync-partials.py`
- ✅ Новая страница — копируй существующий прототип и сразу запусти sync.
- 🔍 Проверка дрейфа (перед деплоем):
  `python3 design/prototypes/build/sync-partials.py --check` (exit 1 = разошлись).

## Новая страница — процедура

1. СНАЧАЛА уточнить у Евгения: вложенность, привязка к меню, URL-слаг.
2. Определить тип страницы по `docs/page-types/README.md` (T01–T12), открыть нужный `T0x.md`.
3. ПОСЛЕ создания прототипа — запись в `structura.md`
   (URL, путь к прототипу, назначение, статус 🟡 «в разработке»).
4. ПОСЛЕ деплоя — статус ✅.
5. Если страница выходит за рамки описанной структуры — обсудить место в иерархии
   и только потом добавлять.
